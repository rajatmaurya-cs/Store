Introduction and Problem Statement

01 / Quality

Software testing helps identify defects.

Detects bugs and weaknesses early before release.

02 / Three Defect Types

Applications have functional, logical, and security issues.

Functional (UI break), Logical (flawed data), Security (leaks).

03 / Method Diversity

Different testing methods reveal different problems.

White-box inspects code, Black-box tests UI, Grey-box tests APIs.

04 / Case Study

The case study compares three testing approaches.

Evaluated directly on our React Native & Supabase demo app.

Key Takeaways
• An application may look completely fine and work smoothly on the screen, but it can still hide severe logic bugs and security weaknesses.
• Different testing methods reveal different problems — Black-box checks visible UI, White-box checks source code, and Grey-box tests API integration.
• The primary goal of testing is to discover and eliminate these defects early before they cause real problems for users.

What is Black-Box Testing?

01 / Scope

Tests application functionality without examining internal source code.

Internal source code structure is unknown to the tester.

02 / Focus

Focuses on inputs and outputs.

Tester gives input, sees output, and evaluates results.

03 / Goal

Checks whether the application behaves as expected.

Matches real output against defined software requirements.

Key Takeaways
• A tester interacts with the application just like an ordinary user, without having any access to the internal source code.
• Testing is focused entirely on providing inputs and evaluating the observed outputs to ensure expected behavior.
• The internal logic and implementation details remain completely hidden from the tester throughout the entire process.

Black-Box Testing in the Case Study

Test 01

Test user registration and login.

Verify valid user accounts can register and log in.

Test 02

Create a comment and verify that it appears.

Enter comment text and verify it shows on screen.

Test 03

Delete a comment and check that it disappears.

Tap delete and confirm comment is removed from list.

Test 04

Test invalid inputs and error messages.

Submit wrong password or empty inputs to check errors.

Key Takeaways
• The tester evaluates the application by checking observable, visible results directly on the mobile interface.
• For example, after submitting a comment, the tester verifies that it immediately appears in the comment feed as expected.
• These test scenarios are illustrative case studies designed to demonstrate how real user interactions are validated.

Black-Box Test Cases and Findings

Test Expected Result Status
Valid login User signs in ✓ Passed
Create comment Comment appears ✓ Passed
Delete comment Comment disappears ✓ Passed
Invalid login Error or rejection ✓ Passed
Key Takeaways
• Black-box testing is highly effective for identifying visible functional errors and user-facing interface defects.
• It confirms that core user workflows, like authentication and commenting, operate properly from an end-user standpoint.
• However, it cannot reveal internal source code defects, such as unused functions, memory leaks, or unhandled exceptions.
Member 3 (Sahil Kumar) • Slide 07

What is White-Box Testing?

01 / Code Level

Examines internal source code and logic.

Tester looks directly inside functions, algorithms, and statements.

02 / Branches

Checks conditions, branches, and execution paths.

Tests every if-else statement, loop, and logical condition.

03 / Implementation

Requires knowledge of the program's implementation.

Tester must understand the programming language and structure.

Key Takeaways
• Unlike black-box testing where the code is invisible, white-box testing looks directly into the inner source code to see exactly how functions work behind the scenes.
• The tester inspects every logical condition, loop, and if-else branch to verify that all possible paths in the software execute correctly and safely.
• By examining the internal program logic, a tester can easily identify faulty calculations, missing validation checks, and unused functions that never get called.
Member 3 (Sahil Kumar) • Slide 08

White-Box Testing in the Case Study

Area 01

Examine comment-handling functions.

Inspect functions that create, fetch, and delete comments to ensure they handle parameters properly.

Area 02

Check authentication and authorization logic.

Verify that the code checks the logged-in user's identity before allowing them to delete or edit a comment.

Area 03

Inspect database operations and connections.

Ensure Supabase queries are properly structured and database connections are safely handled and isolated.

Area 04

Identify unused functions and internal defects.

Locate dead code, leftover test functions, and unhandled error cases that black-box testing cannot see.

Key Takeaways
• In our React Native and Supabase case study, the tester inspects the actual code to make sure a comment can only be deleted by the person who created it.
• By reading through the code directly, white-box testing uncovers hidden bugs like unisolated database queries that might slow down the database or cause memory issues.
• It also identifies dead code and unused functions left behind by developers, helping clean up and secure the application before release.
Member 4 (Puspendar) • Slide 09

What is Grey-Box Testing?

01 / Hybrid

Combines external testing with partial internal knowledge.

Blends user-facing UI actions with backend understanding.

02 / Architecture

May use knowledge of APIs, database structure, or security rules.

Tester knows endpoints, schema tables, and role policies.

03 / Target

Useful for integration and security testing.

Finds data leaks, broken permissions, and API mismatches.

Key Takeaways
• In grey-box testing, the tester does not need full code access, but knows basic things about how the backend and database work.
• This helps the tester test both the mobile app screens and the backend API data at the exact same time.
• It is very useful for catching hidden security leaks and database issues that normal users cannot see on the screen.
Member 4 (Puspendar) • Slide 10

Grey-Box Testing in the Case Study

Test 01

Test access to another user's comments.

Simulate a scenario where User A attempts to view or delete User B's private comments.

Test 02

Examine API responses and database permissions.

Directly monitor HTTP status codes (200 OK vs 403 Forbidden) and payload headers.

Test 03

Check whether Row-Level Security rules prevent unauthorized access.

Verify that PostgreSQL RLS policies block unauthorized queries even if client UI fails.

Test 04

Investigate data-handling and security issues.

Ensure sensitive user tokens, email addresses, and comments are safely isolated.

Key Takeaways
• If User A tries to delete User B's comments, grey-box testing checks whether the Supabase backend blocks this bad action.
• Even if the mobile screen hides the delete button, someone could still send a direct API call, so backend rules must block it.
• This shows why we must test backend security rules and cannot just rely on what looks safe on the mobile screen.
Member 1 (Rajat) • Slide 11

Comparison of All Three Methods

Method Main Focus Perspective Best For
Black-box External behaviour No code access (User perspective) Visible UI defects & user workflows
White-box Internal code Full code access (Developer perspective) Faulty logic branches, dead code, memory leaks
Grey-box Partial internal knowledge Hybrid view (API & schema) Unauthorized access & integration security
Key Takeaways
• Black-box testing ensures the app runs smoothly and looks right for users, while white-box testing verifies that the inner lines of code are written cleanly and without errors.
• Grey-box testing fills the gap in between by testing APIs and database rules using partial knowledge of the system design.
• Each testing method has its own unique strengths, which is why engineering teams use all three together rather than picking just one.
Member 1 (Rajat) • Slide 12

Results, Limitations and Conclusion

No single testing method finds every defect.

Each method inspects different system layers (UI, Code, Database).

Combining testing methods gives broader coverage.

Layering all three methods gives complete software quality assurance.

The paper evaluates one demo application.

Tested on a simplified React Native and Supabase demonstration app.

Manual evaluation without performance metrics.

Does not include automated stress testing or speed benchmarks.

Future work: Automated CI/CD testing.

Future studies could run automated tests across larger enterprise systems.

Key Takeaways
• The biggest takeaway is that overall software quality improves most when black-box, white-box, and grey-box testing are combined together to support each other.
• Because this research study evaluated a single demo app with manual testing, the results should be taken as a helpful guide rather than a universal rule for every company.
• In future projects, adding automated tests and measuring system performance under heavy load would provide even deeper insights into software reliability.
